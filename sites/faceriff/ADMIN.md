# FaceRiff owner dashboard

- Open `/admin/login`, enter an allowlisted email, request the six-digit OTP and verify it; success redirects to `/admin`. The existing customer `/login` remains unchanged (including for the owner).
- `ADMIN_EMAILS` is a comma-separated, case-insensitive **server-only Worker secret**. An empty/missing allowlist denies everyone. Never expose it in client public-config or commit its value. The production owner was confirmed against D1; only that account is allowed.
- Dashboard/data/output routes are GET/HEAD only; the Worker checks the existing better-auth session and verified email before sending private HTML, JSON, or R2 outputs. Anonymous GET/HEAD `/admin` and `/admin/` redirect to `/admin/login`; signed-in non-admins still receive 404. Admin data/output APIs always remain 404 for non-admins. The explicitly public login form/send/verify routes are documented below. `Cache-Control: private, no-store`, noindex and frame-ancestors none are set.
- Endpoints: `/admin`, `/api/admin/dashboard`, `/api/admin/output?job=job_ID`. Output access is restricted to succeeded jobs and their own `jobs/job_ID/N.mp4|webm` R2 prefix. Photos, prompts, tokens and unmasked customer emails are never returned.

## Metrics

Business dates, first-party visitors and displayed timestamps use Asia/Shanghai (UTC+8). Cloudflare history is the explicit exception: its `day_utc` partitions remain UTC. Presets include today and the preceding 6/29 days; today is partial. Custom ranges are capped at 90 days.

- Visitors: successful browser HTML document requests, first-party HMAC-SHA256(IP + user-agent + Shanghai day), keyed using the existing auth secret with a separate analytics context. No cookie, raw IP, raw UA, path or cross-day identifier is stored. Known bots, admin, APIs, static files and prefetch are excluded. Daily deduplication uses the D1 composite primary key. SPA-only navigations are not additional document visits. Shared IP/UA can undercount; network changes can overcount.
- `daily_visitors` keeps a rolling 90-day window, cleaned on subsequent visits. Collection starts on the first tracked request after deployment (`analytics_meta.tracking_started_at`); earlier days use separately labelled Cloudflare history as a reference when present, otherwise unavailable (never invented zero). Daily totals are summed UV, not cross-day distinct people.
- Cloudflare history is imported separately into `cf_daily_traffic`, using `httpRequests1dGroups` (`uniq.uniques`, `sum.pageViews`, `sum.requests`) from the scoped Analytics:Read API token. The one-time backfill covers 2026-10-29 through 2026-11-11 UTC; the last day is an explicitly partial snapshot. The token was read only from the box environment, was not copied to susu or files, and is not a Worker secret. Wrangler continues using its existing deployment login. No scheduled refresh was added.
- Signups: `user.created_at`.
- Created orders: `orders.created_at`, including pending/expired orders. Paid orders and receipts: `orders.paid_at`, USD only; other currencies shown separately.
- Cash refunded: `payments.amount_refunded`, attributed back to the original order's paid date (not actual refund-event date). Values depend on payment webhook synchronization. This is separate from returned generation credits.
- Jobs and current outcome: `jobs.created_at`; `quality_review` is delivered but marked for review, not counted again as normal succeeded. Active = queued/submitted. Failed/canceled are separate. Counts update as jobs settle.
- Returned-credit jobs: an existing `credit_ledger` refund with `idem_key=refund:job:ID`. May overlap failures; not a cash refund.
- Yir generations: non-skipped IDs in `jobs.upstream_job_id`. Cost uses `upstream_cost_usd` when present, otherwise recorded generation count × $2.7378. An upstream charge accepted before its ID was persisted cannot be captured.
- Estimated difference = USD receipts − associated cumulative cash refunds − Yir cost. Includes test jobs/retries, excludes Cloudflare, payment fees, tax, etc.; not accounting profit or per-order gross margin.
- Recent lists are capped at 100 within the selected range. Orders buy credits; jobs have no `order_id`. The displayed same-account job counts are explicitly **not** order-to-video attribution.
- Quality holds include all historical failed `swap_not_applied` / `swap_not_applied_v2` jobs, grouped by account/template, matching the existing retry guard. No unlock or credit-changing actions are present.

## Cloudflare backfill semantics

- The daily reference column prefers `daily_visitors` (including a real zero) and otherwise uses the imported CF unique count. `daily.visitors` in the API remains first-party-only; `cfVisitors`, `cfPageViews` and `cfRequests` are separate fields. KPI totals for each source remain separate and are never added together.
- The same date string represents different windows: CF UTC 2026-11-10 is Shanghai 2026-11-10 08:00 through 2026-11-11 08:00. Daily zone aggregates cannot be correctly shifted by eight hours into exact Shanghai-day unique counts; no such conversion is attempted. Do not derive order conversion rates from these mismatched windows.
- CF zone traffic may include crawlers, threats, API calls, static assets, the admin and www hosts. Requests are not people; page views are not unique visitors; summed daily UV is not a cross-day unique population. The first-party launch day is also partial.
- `cfHistory` reports the imported range, dataset, latest fetch timestamp and partial UTC dates. Missing dates remain null; data outside the saved range is not assumed zero. Partial snapshots remain partial even after the calendar day has ended until a newer import replaces them.
- Metric SQL is kept in ignored `.wrangler/`, never mixed with schema migrations or committed. Its UPSERT is keyed by `day_utc`; only a same/newer fetch may replace a row, and a complete row cannot be downgraded to a partial snapshot. Imports never modify `daily_visitors` or `analytics_meta`.
- Apply the additive schema migration with the existing local Wrangler, then `pnpm exec wrangler d1 execute DB --remote --file .wrangler/<data-only-backfill>.sql`. Before/after counts and the previous deployment are backed up in `.wrangler/cf-history-backup-20261111/`. The production Worker only reads D1; dashboard visits do not call the Analytics API.
- Future refresh is optional. It would need separately provisioning the scoped token as a Worker secret through an approved secure path, plus a small scheduled fetch. This release intentionally does neither; first-party tracking continues normally after the historical backfill.

## Dedicated admin sign-in entry

- Public, noindex/noarchive, private/no-store HTML at /admin/login. Forms work without JavaScript, with same-origin-only POST /admin/login/send and /admin/login/verify. CSRF Origin check, bounded 2 KB form bodies, escaped form values, no arbitrary callback URL and no OTP/email in query strings. Existing dashboard CSP and security headers apply, except the login HTML uses Referrer-Policy: same-origin so browser form POSTs retain a verifiable Origin (no-referrer can produce Origin: null). No cross-origin referrer is sent.
- Both POST handlers normalize email (trim/lowercase) and enforce the same server-only ADMIN_EMAILS allowlist BEFORE calling better-auth or looking up a customer. Every non-allowlisted email gets the same generic 403 无权访问, irrespective of customer existence. An empty/missing allowlist denies all. The page never lists or prefills authorized addresses.
- Authorized send delegates internally to the existing better-auth handler at /api/auth/email-otp/send-verification-otp, hard-coded type sign-in. Verify delegates to /api/auth/sign-in/email-otp, preserves every better-auth Set-Cookie header and redirects 303 to /admin. No custom sessions or alternative OTPs are minted. The existing 6-digit/10-minute expiry, attempt limits, email delivery and authentication behavior remain in better-auth.
- Extra fixed-window limits use existing quota_counters (no migration): 5 send attempts per IP per 15 minutes, 3 sends per authorized email per 15 minutes, 10 verify attempts per IP per 15 minutes. Keys are HMAC-SHA256 of a domain-separated, daily identifier using the existing auth secret; no raw IP/email/code is saved by these counters. Only admin-login-prefixed buckets older than two days are pruned. Missing IP/secret or storage failure denies access. Better-auth's original database-backed limits still apply.
- This is an additional entry gate, not a separate identity system or MFA factor. Customer login is deliberately unchanged and may still send a code to the owner. Either valid session must pass ADMIN_EMAILS and verified-email checks at /admin and admin APIs. Login send/verify are intentionally separate public auth forms, not protected data APIs.
- Anonymous dashboard GET/HEAD redirects 302 only for /admin and /admin/; other unknown admin URLs stay 404, signed-in non-admins stay 404, and data/output APIs never redirect to login. An unauthenticated /admin Not found in older releases was intentional, not a broken account.
- Validation uses mocked auth/delivery handlers for allowed send and cookie propagation; no real owner OTP is sent and no owner session is minted during deployment. Production denial checks use reserved example.invalid emails and confirm no matching verification records were created.

## Paid-failure hold (unblocking a customer)

- Trigger `jobs_quality_retry_guard` (migration `20261112090000_paid_failure_guard.sql`) and `qualityRetryHold` in `packages/jobs/src/lifecycle.ts` block a new paid job for the same user and model while that user has a `failed` job with `error_code` `swap_not_applied`/`swap_not_applied_v2`, or a job Yir already accepted (`upstream_job_id` set) that failed with `internal_error`, `stale`, `timeout` or `check_failed`. The customer sees HTTP 409 `quality_review_required`; credits were refunded once and are safe.
- Why: after Yir accepts a task we are charged (~$2.74) even when our store/compose/check fails, so a refunded self-retry could burn upstream spend repeatedly.
- The raw Yir output is usually still in R2 at `jobs/<job_id>/0.mp4` (not served to the customer while the job is failed). Deliver it manually or re-compose it rather than regenerating.
- To unblock after review, rename the error code to `*_reviewed` (one job at a time):
  `pnpm exec wrangler d1 execute faceriff --remote --command "UPDATE jobs SET error_code = error_code || '_reviewed' WHERE id = 'job_ID' AND status = 'failed';"`
  Back up the row first; verify `changes = 1`.
- Cancel: `/api/jobs/<id>/cancel` now returns 409 `not_cancellable` once the job is submitted to Yir (no UI button uses it); only queued jobs can be canceled and refunded.
## Manual review queue (`/admin/review`, 待审核任务)

- `tiny-desk` has `manualReview: true` (site.models.ts). After Yir renders and the face check runs: a clear pass is delivered automatically as before. A clear fail, a grey zone (`review`), or a checker outage does **not** refund and does **not** deliver: compose still runs, then the job moves to status `needs_review` with `error_code` `review_swap_fail` / `review_grey` / `review_check_error`. If compose itself fails after the render, the job is held as well (`review_compose_failed`, or alongside one of the codes above) with the raw Yir output `jobs/<id>/0.mp4` as the preview; approving it delivers that raw file (Yir audio, shots not re-timed).
- While held: credits stay spent; `outputs_json` and `review_json` (per-role scores, verdicts, threshold, raw key, compose error) are stored, but `/files/...` keeps returning 404 and `/api/jobs` returns no outputs and no error code. The customer sees "Your video is being reviewed by our team for quality. You'll get an email within 24 hours." No email is sent at this point.
- Retry hold: while a job is `needs_review`, the same user cannot start another paid job of that model (HTTP 409 `review_pending`, enforced in the handler and atomically by the D1 trigger `jobs_review_pending_guard`). It ends automatically with the decision; other models are unaffected.
- Never auto-settled: the stale-on-read sweeper (`healStale`, model timeout + 15 min), the runner timeout and the cancel endpoint only touch `queued`/`submitted` jobs, so a held job waits however long it takes. The runner treats `needs_review` as terminal and still records `upstream_cost_usd`.
- The dashboard header shows a 待审核任务 badge with the pending count (red when > 0) plus a notice linking to `/admin/review`. Daily/order "待复核" counts include held jobs.
- `/admin/review` (same allowlist/session check, non-admins 404, anonymous GET redirects to `/admin/login`): oldest first, each item shows job id, the customer's **full email** (shown only here, so the owner can follow up), created and held times in Asia/Shanghai, template, reason, per-role similarity/verdict/peak/strong-frame counts against the threshold, and an inline player. Video comes from `/api/admin/review-video?job=ID[&v=raw]` (admin-only, Range-capable, confined to `jobs/<id>/N.mp4|webm`; final composed video by default, raw on request).
- Buttons 通过并交付 / 拒绝并退积分 open a confirmation page (no JavaScript; CSP stays `default-src 'none'` plus `media-src 'self'`). Confirming POSTs to `/admin/review/action`, the only admin POST route; it requires the admin session, `Origin: https://faceriff.com` and a non-cross-site `Sec-Fetch-Site`.
  - Approve: `needs_review → succeeded`, error cleared, outputs served, the usual "video is ready" email. Credits stay spent.
  - Reject: `needs_review → failed` with `error_code = <code>_reviewed` (e.g. `review_grey_reviewed`), credits refunded once via the idempotent `refund:job:<id>` ledger entry, the usual "couldn't be made, credits are back" email. `_reviewed` codes match neither retry guard, so the customer can buy again.
  - Each decision is a conditional UPDATE from `needs_review`; repeats/double clicks are no-ops (no second refund or email; a repeated reject re-runs the idempotent settlement in case a refund write failed). If the customer email fails, the decision still stands and the page shows a red notice to follow up by hand (`review_email_failed` log event). A reject that stopped halfway (refund or log write failed) is finished by clicking reject again. Decisions are logged in `job_reviews` (job, action, admin email, previous code, time) and as `admin_review_decision` log events (no customer data). The page lists the last 30 days of decisions.
- Migration `20261112100000_manual_review_queue.sql`: `jobs.review_json`, table `job_reviews`, index `jobs_status_idx`, trigger `jobs_review_pending_guard`. Hand-written like the earlier guard migrations (not in the drizzle journal).
- Manual fallback (e.g. without the page): approve `UPDATE jobs SET status='succeeded', error_code=NULL, error_message=NULL WHERE id='job_ID' AND status='needs_review';` (sends no email); to reject, use the page so the refund goes through the ledger.

## Realtime visitors and charts

- The top of `/admin` shows **realtime visitors** (online in the last 5 and 30 minutes, page views per minute averaged over 5 minutes, a 30-minute per-minute sparkline, active pages, countries and devices for the last 30 minutes) and **charts**: hourly visitors/page views for the last 48 hours (Asia/Shanghai hours), daily visitors/page views for the last 30 days (first-party solid lines, Cloudflare history dashed and labelled UTC; never added together), daily orders next to stacked succeeded / needs_review / failed jobs (Shanghai creation day), and 30-day first-party device (donut), country, OS, browser and referrer shares. A collapsible table shows the exact daily numbers. Charts are server-rendered plain SVG/HTML (no chart library, no external requests); on phones the time charts scroll sideways and start at the newest day.
- The realtime block refreshes itself every 2 hours (checked once a minute while the tab is visible; returning to the tab refreshes only if the last refresh was over 2 hours ago; a manual page reload is always fresh because the page and JSON are `no-store`) from `GET /api/admin/realtime` and shows the last update time in Beijing time. The endpoint has the same allowlist check as the rest of admin (404 for anonymous and non-admin users, no redirect), `Cache-Control: private, no-store`. The dashboard page alone allows one inline script through a per-response CSP nonce (`script-src 'nonce-…'; connect-src 'self'`); the script only writes text (`textContent`), never HTML from data.
- Collection: the same qualifying requests as daily visitors (successful browser HTML documents; bots, prefetch, `/admin`, `/api`, `/files`, static files excluded) are added to the existing single D1 batch per page view, so there is no extra round trip. `visitor_hits` keeps one row per (minute, visitor, page) with a hit counter (repeat views in the same minute update the row); `visitor` is the first 16 hex characters of the existing daily HMAC (IP + UA + Shanghai day), no cookie, raw IP or UA. Pages are an allowlist of public routes; token pages collapse to `/phone/*`, anything else is `other` (no raw paths or query strings). Country/device/OS/browser/referrer use the same coarse classes as the daily dimensions. Rows older than 48 h are deleted by a primary-key range delete on each write (normally zero rows). `daily_pageviews` counts every qualifying page view per Shanghai day, 90 days.
- Limits: realtime, hourly and first-party page-view data start at the first visit after the deploy (`analytics_meta.realtime_started_at`); earlier hours/days show as gaps, not zero. Only full document loads are counted (in-app navigations without a page load are not), so page views are a lower bound. "Online" means a qualifying page load in the window (no heartbeat), so a reader who stays on one page for over 5 minutes drops out of the 5-minute count. The daily hash changes at Shanghai midnight, so one person can appear twice in windows spanning midnight. Shared IP + UA undercounts, network changes overcount.
- Migration `20261112110000_realtime_visitors.sql` (additive): tables `visitor_hits` and `daily_pageviews`. Tests: `test/realtime.test.ts`.

## Localization data (country and browser language)

- Visitors: the first-visit dimensions now include `language` (primary Accept-Language entry, highest q, as a short tag such as `en-US`, `pt-BR`, `es-419`, `zh-CN`; `zh-Hans`/`zh-Hant` map to `zh-CN`/`zh-TW`) and `lang_base` (`en`, `pt`, …). Only a whitelist of ~45 base languages is kept; anything else is `other`, a missing header is `unknown`. Same privacy model as the other dimensions (daily first visit, no cookie/IP/UA/raw header).
- Signups, orders and payments: migration `20261112160000_conversion_geo.sql` adds nullable `user_attribution.signup_country/signup_language` and `orders.country/language/paid_country/paid_language` (country = `request.cf.country`, never an IP; language = the same short tag). The core package schema is unchanged; faceriff's thin route wrappers stamp them after the core handler succeeds, and failures are only logged (`signup_geo_failed`, `order_geo_failed`, `payment_geo_failed`), never break sign-in or checkout:
  - signup: `/api/auth/*` responses that set a session cookie → the session's user, only if that account's attribution row was created in the last 15 minutes and is still unstamped (returning users are untouched);
  - order: `/api/billing/checkout` stamps the new order once;
  - payment: `/api/billing/sync` (the buyer's own return page) stamps `paid_*` once when it reports `paid`. Provider webhooks come from PayPal/Stripe servers and carry no buyer location, so a payment captured only by webhook keeps `paid_*` NULL; the dashboard attributes payments to the order's checkout country/language.
- Dashboard section "本地化决策" (last 30 Shanghai days): Europe + North America / US / Europe / other cards (share of visitors with signups, paid orders, revenue), a market table (US, Canada, Europe incl. UK/CH/NO, other, unknown, not recorded), visitor language / base language / country share bars, and conversion tables by country and by base language: visitors (summed daily first-visit UV), signups, orders created, paid orders, USD revenue, signup rate (signups ÷ visitors), paid conversion (paid ÷ visitors), order pay rate (paid ÷ orders).
- Limits: languages and the new columns start at this deploy; earlier visitors have no language and earlier signups/orders show as "未记录". Country is the network exit (VPN/proxy can change it). Visitor UV is summed per day and is not a cross-day unique count, so rates are directional only, especially with few orders. No backfill from `signup_ip` was attempted (no external geo lookup).
